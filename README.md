# Fadaa Locative

> A modern property and rental management platform for agencies, landlords, and tenants.

Fadaa Locative centralizes property management, leases, payments, rent receipts, maintenance requests, notifications, agency teams, subscriptions, and tenant communication in one application.

## Overview

The project is organized as a full-stack application:

| Layer | Technology | Location |
| --- | --- | --- |
| Frontend | Next.js 16, React 19, Bootstrap, Leaflet | [`gestion-location-frontend/`](./gestion-location-frontend) |
| Backend | FastAPI, SQLAlchemy, Alembic, Python 3.12 | [`gestion-location-backend/`](./gestion-location-backend) |
| Database | PostgreSQL 16 | Docker Compose |
| Authentication | JWT access and refresh tokens | Backend |
| Notifications | Firebase Cloud Messaging (optional) | Backend |

## Features

- Authentication, user profiles, roles, permissions, and agency members
- Agencies, properties, lots, categories, tenants, and owners
- Lease and mandate management
- Due dates, payments, charges, and downloadable rent receipts
- Maintenance requests, complaints, discussions, reviews, and notifications
- Subscription plans, trials, usage limits, and plan change requests
- Property photos and file uploads
- Blog posts and public demo/contact requests
- Dashboard statistics and action history auditing
- OpenAPI documentation generated by FastAPI

## Quick start with Docker

### Prerequisites

- [Docker Desktop](https://www.docker.com/products/docker-desktop/)
- Git

### 1. Clone the repository

```bash
git clone git@github.com:yascoree/FADAA-Locative.git
cd fadaa-locative
```

### 2. Create the environment file

Create a `.env` file in the repository root. Docker Compose reads these values when it starts PostgreSQL and the application services:

```dotenv
POSTGRES_USER=gestion_user
POSTGRES_PASSWORD=change_me
POSTGRES_DB=fadaa_locative_db
POSTGRES_HOST_PORT=5435
```

For a complete backend configuration reference, see [`gestion-location-backend/.env.example`](./gestion-location-backend/.env.example).

### 3. Start the stack

```bash
docker compose up --build
```

The services will be available at:

- Frontend: <http://localhost:3000>
- Backend: <http://localhost:8000>
- Swagger UI: <http://localhost:8000/docs>
- ReDoc: <http://localhost:8000/redoc>
- PostgreSQL: `localhost:5435`

The backend automatically applies Alembic migrations when the Compose service starts.

### Stop the stack

```bash
docker compose down
```

To also remove the local PostgreSQL volume and all stored database data:

```bash
docker compose down -v
```

## Local development

Docker is the recommended way to run the complete stack. The following instructions are useful when developing one service directly.

### Backend

Requirements: Python 3.12+ and a running PostgreSQL instance.

```bash
cd gestion-location-backend

# Windows PowerShell
py -3.12 -m venv .venv
.\.venv\Scripts\Activate.ps1

pip install -r requirements.txt
copy .env.example .env
alembic upgrade head
uvicorn app.main:app --reload --port 8000
```

The API is then available at <http://localhost:8000>.

To create or update the trial subscription assignments used by existing agencies:

```bash
python seed.py
```

### Frontend

Requirements: Node.js 22+ and npm.

```bash
cd gestion-location-frontend
npm install
npm run dev
```

By default, the frontend uses `http://localhost:8000` for the API. To override it, create `gestion-location-frontend/.env.local`:

```dotenv
NEXT_PUBLIC_API_URL=http://localhost:8000
```

Available frontend scripts:

```bash
npm run dev       # Start the development server
npm run build     # Create a production build
npm run start     # Serve the production build
npm run lint      # Run ESLint
```

## Configuration

The backend reads its configuration from environment variables. Never commit real credentials or Firebase service-account files.

| Variable | Purpose | Example |
| --- | --- | --- |
| `DATABASE_URL` | PostgreSQL connection string | `postgresql://gestion_user:change_me@localhost:5435/fadaa_locative_db` |
| `SECRET_KEY` | JWT signing secret | `replace-with-a-long-random-secret` |
| `ALGORITHM` | JWT algorithm | `HS256` |
| `ACCESS_TOKEN_EXPIRE_MINUTES` | Access-token lifetime | `1440` |
| `REFRESH_TOKEN_EXPIRE_DAYS` | Refresh-token lifetime | `30` |
| `FIREBASE_CREDENTIALS_PATH` | Firebase service-account JSON path | Optional |
| `PUSH_ALERT_DAYS_BEFORE` | Days before an event to send an alert | `3` |
| `PUSH_OVERDUE_REMINDER_EVERY_DAYS` | Overdue reminder interval | `3` |

When Firebase is not configured, push notifications remain disabled while the rest of the application can run normally.

## API and database workflow

### API documentation

FastAPI exposes interactive documentation once the backend is running:

- Swagger UI: <http://localhost:8000/docs>
- ReDoc: <http://localhost:8000/redoc>
- OpenAPI schema: <http://localhost:8000/openapi.json>

### Database migrations

Run migrations from `gestion-location-backend/`:

```bash
alembic upgrade head
```

Create a migration after changing SQLAlchemy models:

```bash
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```

## Security notes

- Use strong, unique values for `SECRET_KEY` and `POSTGRES_PASSWORD`.
- Keep `.env`, Firebase credentials, uploads, and database volumes out of version control.
- Restrict CORS origins before deploying to production.
- Run the application behind HTTPS in production.
- Do not use development reload mode in production.
- Review generated migrations before applying them to a shared database.

## Contributing

1. Create a focused branch from the current development branch.
2. Keep backend and frontend changes scoped and documented.
3. Run the relevant tests, lint checks, and build before opening a pull request.
4. Include migration files when changing the database schema.
5. Never commit secrets, local environment files, generated build output, or dependency caches.
